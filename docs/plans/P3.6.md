## Context

PLAN.md P3.6: "Task lifecycle: end/expire tasks; evict finished tasks and outcomes from the
bridge (history stays in the audit log)." Added 2026-11-11 (Decisions): "`tasks`/`outcomes`
grow without bound". P8 wants the bridge always on, so every request would leak one `Task`
and every confirmation one outcome, for weeks.

Three gaps, one per section:

- A. Nothing ever leaves `tasks` or `outcomes`. Also P2 gate review nit (e): a task stopped
  by a budget breach keeps its pending action in the UI list until its 120 s run out.
- B. The core cannot say "this request is over". A task stays usable for the rest of its
  120 s after the answer was given. `ToolExecutor` leaks its worker thread on a timeout
  (`docs/plans/P3.5.md`, Facts), so a late call on a finished request is possible.
- C. The core does not use B.

Facts that shape the design (checked 2026-11-16):

- A task older than `MAX_SECONDS` can never act again: `Policy._check` and `_recheck`
  refuse it and stop it. So age alone decides when a task is dead. No "finished" flag is
  needed for eviction.
- The core polls `/outcome` for at most `MAX_SECONDS` from the moment `/tool` answered 202
  (`core/tools.py` `_wait`). The 202 needs a passing `Policy.check`, so it comes within
  `MAX_SECONDS` of the task's start. So no honest reader asks for an outcome later than
  `2 * MAX_SECONDS` after its task started.
- `tasks` only grows in `/task`. `outcomes` only grows for an action that was queued, and
  every queued action belongs to a task. So one sweep, run in `/task`, bounds both.
- An evicted task is answered by the existing unknown-task path: `/tool` -> 404
  `Unknown task`, logged as `request` with `decision: deny`. Nothing new to refuse.
- `stop()` already drops every pending action with outcome `cancelled`.
- No task is evicted while its handler runs. The longest handler is `run_named_script`,
  bounded at 65 s (timeout at most 60 s in `config/scripts.toml`, plus 5 s; P3.7 C). A
  handler starts no later than `MAX_SECONDS` into its task (`recheck` refuses after), so it
  ends before `KEEP`. Before P3.7 C a hung script had no bound.
- A stopped task's pending action still waits in the queue until its time runs out
  (P2 gate review nit (e), checked 2026-11-20: `expire()` has no `stopped` branch). D3
  closes it.

## Section D — Ctrl+C ends the task now (commit `P3.6: Ctrl+C ends the task`)

Status: APPROVED by Karthik 2026-11-20. Not implemented.

Why. Manual step 2 failed on `f6f0526`. Ctrl+C at `pending <id>` did not cancel the
action: the audit had `expired` at task start + 120 s and `end` 8 ms later with
`cancelled: null`. Cause: OpenJarvis runs each tool on a worker thread and the main
thread waits in `future.result(timeout=...)` (`OpenJarvis/src/openjarvis/tools/_stubs.py:449`).
On Windows, CPython 3.12 cannot interrupt one long lock wait with Ctrl+C; the
`KeyboardInterrupt` is raised only when the wait returns, which is when the worker's
`/outcome` poll ends at the expiry. Then C's `finally` sends `/end`, too late. The
bridge was not at fault: it logged `end` 8 ms after the core sent it. Reproduced by
Claude Code on 3.12.10 (a 4 s worker, SIGINT at 0.5 s): `future.result(timeout=60)` is
interrupted at 4.0 s, a `join(0.2)` loop at 0.6 s; `_thread.interrupt_main()` behaves
like the real signal.

```python
def _handle(core, text):
    box = []

    def run():
        try:
            box.append((True, core.handle(text)))
        except BaseException as error:  # handed to the main thread below
            box.append((False, error))

    thread = threading.Thread(target=run, daemon=True)
    thread.start()
    try:
        while thread.is_alive():
            # ponytail: short waits. On Windows (CPython 3.12) Ctrl+C cannot interrupt one
            # long lock wait (OpenJarvis' future.result); it lands between these.
            thread.join(0.2)
    except KeyboardInterrupt:
        core.cancel()
        raise
    ok, value = box[0]
    if not ok:
        raise value
    return value
```
