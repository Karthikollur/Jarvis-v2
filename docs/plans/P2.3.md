# P2.3 — confirm queue

## Context

After P2.2, `POST /tool` answers 409 for anything the policy marks `confirm` (every T2 action,
and T1 actions on a tainted task) and nothing runs. P2.3 adds the queue that holds those
actions until Karthik approves or denies them through the UI. PLAN.md 4.1: a click or key
press in the UI is the only approval path; voice and the model can never approve.

Outcome: a pending action can be listed, approved or denied only with the `ui` token; an
approved action runs exactly as it was requested, once, through the same code path as any
other tool. No UI yet (P6): tests play the UI role.

## Design

**Flow**

1. core `POST /tool` -> policy says `confirm` -> bridge stores a pending action and answers
   `202 {"pending_id": ...}`. Nothing runs.
2. ui `GET /pending` -> list of pending actions: id, tool, raw args, resolved paths, reason
   (`T2` or `tainted T1`), age.
3. ui `POST /approve {pending_id}` -> bridge re-validates, runs the handler, stores the
   outcome. ui `POST /deny {pending_id}` -> stores outcome `denied`.
4. core `POST /outcome {pending_id}` -> `pending | done | failed | denied | expired`, plus the
   tool result when `done`. Core polls this (no long-poll; simplest thing that works).

**Rules**

- A pending action is immutable and one-shot. Approve or deny removes it from the queue;
  a second approve gets 404. What is approved is exactly what was stored, never new arguments.
- Re-validation at approve time (new `Policy.recheck(task, tool, args, paths)` in
  `safety/policy.py`): task not stopped, time budget not exceeded, and every path argument
  resolved again must equal the path resolved at request time. A junction swapped in while
  the action waited is therefore refused. Failure -> outcome `expired`/`denied`, nothing runs.
- **Decision for Karthik: waiting time counts against the task's 120 s.** No click within the
  task window -> the action expires (approve answers 410). Strict and simple; the alternative
  (pause the clock while waiting) lets a forgotten dialog approve a stale action later.
- One pending action per task: while one waits, further `/tool` calls for that task get 409
  `awaiting confirmation`. Global cap of 16 pending actions; beyond that `confirm` requests
  are refused 429-style (403 with reason). Limits confirmation flooding.
- `ConfirmQueue.clear()` exists for the kill switch (P2.5). No route calls it yet.
- Handlers still have exactly one call site: `/tool` and `/approve` both go through one inner
  `execute(task, tool, args, paths)` function in `create_app`, which also calls
  `Policy.record`.

**Roles (`bridge.app.ROUTE_ROLES`)**

| Path | Roles |
|---|---|
| `GET /pending` | `ui` |
| `POST /approve` | `ui` |
| `POST /deny` | `ui` |
| `POST /outcome` | `core` |

Same limit as recorded for audit point 8: any process running as Karthik can read `ui.token`.
