## Part 4 — P2.4 plan

### Context

PLAN.md 4.2: "Audit log. Append-only JSONL of every tool request, policy decision, and result."
Later phases depend on it: P3 "every step appears in the audit log", P6.4 audit view, P8 "zero
unconfirmed T2 actions in the audit log". Today nothing is recorded: a denied request, an
approval, or a tool run leaves no trace.

Outcome: every tool request, decision, approval, denial, expiry and result is one JSON line on
disk, written **before** the action it describes. If the line cannot be written, the action
does not run.

### Design

**Module** `safety/audit.py` (new, about 30 lines, stdlib only):

- `AuditLog(path, wall=time.time)`; `write(event, **fields)` appends one line
  `{"ts": <UTC ISO 8601>, "event": ..., ...}` with
  `json.dumps(..., default=str, ensure_ascii=False)`, under a `threading.Lock`, opening the
  file in append mode per write and flushing. No method to edit, truncate or delete.
- `json.dumps` escapes newlines, so a model-supplied argument cannot forge a second log line.
  This gets a test.
- `write` lets `OSError` propagate. The caller fails closed.
- Results are logged as text cut to 2000 characters with `"truncated": true` when cut
  (`read_text_file` returns whole files). Args are logged in full: they are what was approved.

**File**: `%LOCALAPPDATA%\Jarvis\audit.jsonl`. `create_app` refuses a symlink or junction at
that path, creates the file, and applies the existing `bridge.app.protect` (user-only ACL),
the same way `load_token` treats token files. `safety/` does not import from `bridge/`.
`# ponytail:` one file, no rotation; rotate by date when the P6.4 view gets slow.

**Events** (bridge writes them; `Policy` stays free of I/O):

| Event | When | Fields |
|---|---|---|
| `start` | bridge start | — (marks that in-memory pending actions were dropped) |
| `task` | `POST /task` | `task_id` |
| `request` | every `POST /tool`, after `Policy.check`, before anything runs or queues | `task_id`, `tool`, `args`, `decision`, `reason`, `tier`, `paths`, `tainted`; unknown task is logged with decision `deny` |
| `queued` | action stored | `task_id`, `pending_id`; or `refused` + reason when the queue is full or the task already waits |
| `approve` | ui approved, after `recheck`, before the handler | `pending_id`, `task_id`, `tool`, `recheck` (`ok` or the refusal) |
| `deny` | ui denied | `pending_id`, `task_id`, `tool` |
| `expired` | task window passed while waiting | `pending_id`, `task_id`, `tool` |
| `result` | handler returned, raised, or is missing | `task_id`, `tool`, `pending_id` if any, `status` (`done`/`failed`/`not_implemented`), `result` or `error` (exception type and text; Karthik's log, never returned to the model) |
| `forbidden` | a valid token used on a route its role may not call | `role`, `path` (catches core trying to approve) |

Requests with no valid token are not logged: any local process could flood the file.

**Fail closed**: a failed audit write before execution -> 500 `Audit log unavailable`, the
handler is not called, a queued action is taken back out. A failed `result` write after the
handler ran -> 500 and `task.stopped = True`, so nothing further runs unlogged; the `request`
line without a `result` line shows the outcome is unknown.

**Limit, to record in Decisions**: any process running as Karthik can edit the file (audit
point 6). "Append-only" means Jarvis code only appends. No hash chain: it would not stop a
same-user attacker, who can recompute it.

**C. `P2.4: bridge writes the audit log`** — tick P2.4.
Files: `bridge/app.py`, `tests/test_bridge.py`, docs.

- `create_app` prepares `storage / "audit.jsonl"` as above and writes the events in the
  table. `Authenticate` gets the log for `forbidden`. `execute()` stays the only handler
  call site; it writes `result`.
- Tests, each forbidden case asserted not executed (victim file or folder checked):
  - allowed tool -> `request`(allow) then `result`(done), in that order.
  - denied request (outside root, unknown tool, unknown task) -> `request`(deny), no `result`.
  - T2 flow -> `request`(confirm), `queued`, `approve`(ok), `result`(done), ids matching;
    deny flow -> `deny`, no `result`; expiry -> `expired`, no `result`.
  - junction swapped in while waiting -> `approve` line carries the refusal, no `result`.
  - failing handler -> `result`(failed) with the error text, and the HTTP body still hides it.
  - core token on `/approve` -> `forbidden` line; wrong token -> no line.
  - audit write patched to raise: `/tool` -> 500 and the folder is not created; `/approve`
    -> 500, the file is not deleted, the action is not left runnable.
  - `result` write raising after the handler ran -> 500 and the task's next call is refused.
  - audit file is a junction at startup -> `create_app` raises; the file's ACL is user-only
    (same check as `test_real_acl_and_persistence`).
  - invariant test: across one scripted session, every `result` line is preceded by a
    `request` line with decision `allow`, or by an `approve` line with `recheck: ok`, for the
    same task and tool.
