## Context

PLAN.md P5: push-to-talk -> STT (CPU) -> core -> Piper TTS (CPU); streaming TTS; barge-in;
wake word off by default with a visible mic indicator; a test that voice cannot approve T2.
Done when: "Jarvis, what's in my sandbox folder?" gets a spoken answer within targets
(simple answer starts within 3 s, single tool command within 5 s), 10 runs in a row.

What voice changes in the threat picture:

- A microphone hears anyone: a video, a call, a person in the room. PLAN.md 4.1 already
  says a spoken "yes" never approves T2. The same reasoning applies to T1 when nobody
  pressed a key (D3).
- Speech recognition invents text on silence and noise ("Thank you."). An invented
  sentence is a request like any other.
- The reply is spoken aloud: a long or strange model answer is now audible, and file names
  and paths are read out to whoever is near.

## Design in one page

One new process: `python -m voice`. It builds `Core` in-process (`core.agent.build`) and
runs one loop:

```
hotkey press -> record until silence or second press -> transcribe -> Core.handle
            -> split answer into sentences -> synthesise and play, sentence by sentence
hotkey press while speaking or thinking -> stop playback, core Stop, listen again
```

- `voice/audio.py`: microphone in, speaker out (`sounddevice`). The only module that
  touches a device.
- `voice/stt.py`: `transcribe(samples) -> str` (faster-whisper, CPU, English fixed).
- `voice/tts.py`: `synthesise(sentence) -> samples` (Piper, CPU).
- `voice/loop.py`: the state machine. Takes plain callables (`listen`, `transcribe`,
  `handle`, `speak`, `stop`), so every test runs with fakes and no audio hardware.
- `voice/__main__.py`: wires the real parts, reads `config/voice.toml` and the hotkey.
- States: `idle`, `listening`, `thinking`, `speaking`, plus `waiting for approval` (a
  sub-state of thinking). One `on_state(name)` callback; P5 prints it, P6 draws it.

No server, no IPC in P5. The voice process is also the first long-running core process.

## Decisions for Karthik

- D1. Dependencies (each needs your yes; each downloads native code): `faster-whisper`
  (brings `ctranslate2`, `onnxruntime`, `av`, `tokenizers`, `huggingface_hub`),
  `piper-tts`, `sounddevice`, later `openwakeword` (brings `scipy`, `scikit-learn`,
  `requests`). Models are downloads too: a Whisper model (`base.en` 148 MB or `small.en`
  486 MB), one Piper voice (63 MB), later the wake-word, melspectrogram and embedding
  models. At runtime everything loads from a local folder (`%LOCALAPPDATA%\Jarvis\models`)
  by path, with `HF_HUB_OFFLINE=1` as a second guard so nothing phones home. Licences:
  `piper-tts` is GPL-3.0-or-later; openWakeWord's pretrained models are CC BY-NC-SA 4.0
  (non-commercial). Fine for a personal tool that is never shipped or sold; if Jarvis is
  ever distributed, both need another look.
  Alternative for STT/TTS: OpenJarvis's own `speech/` backends (faster-whisper, Kokoro);
  not recommended: thin wrappers around the same libraries plus a registry we do not need.
- D2. Talk key: press once to start, recording ends on silence (or a second press). Not
  hold-to-talk. Reason: hold-to-talk needs key-up events, which `RegisterHotKey` does not
  give; the other way is a low-level keyboard hook, which sees every keystroke on the
  machine. Recommended default `Ctrl+Alt+Space`, in `config/hotkey.toml` as `talk`.
- D3. A request that started from the wake word (nobody pressed a key) opens a tainted
  task: every T1 action waits for a click. Recommended. Needs one small bridge change:
  `POST /task` body gains `untrusted: true` (StrictBool), which makes that task tainted and
  sets the conversation taint; with a refusal test. A request started by the talk key is
  treated as today.
- D4. Barge-in by the talk key only. PLAN.md P5.3 says "speaking or the hotkey". Voice
  barge-in on laptop speakers means the microphone hears Jarvis itself; it needs echo
  cancellation. Recommended: key only in v1; with the wake word on, the wake word is
  ignored while Jarvis speaks.
- D5. Streaming (P5.2) is sentence-level, after the model has finished: sentence one plays
  while sentence two is synthesised. The model is not streamed token by token, because the
  agent loop does not stream and replies are one short sentence by prompt rule 6. Token
  streaming gets its own plan only if section A measures the 3 s target missed because of
  generation time on long answers.
- D6. Where the latency clock starts: at end of speech as detected (silence), not at the
  key press. The silence wait itself (about 0.6 s) is reported separately.
- D7. Conversation: a request within 90 s of the last answer continues the conversation
  (`fresh=False`); later than that, or after a spoken "new conversation", it is fresh.
  Consequence to accept: inside a continued conversation taint stays, so T1 actions keep
  needing clicks after any `list_dir` or `recall_memory`.
- D8. Keep the chat model loaded (PROGRESS.md open question "Keep-alive"). Recommended:
  you set the user variable `OLLAMA_KEEP_ALIVE=-1` once; no code. Alternative: the voice
  loop pings Ollama, which must use the same `num_ctx` or it causes the reload it is meant
  to prevent.
- D9. Spoken output cap: 400 characters, then "the rest is on screen". Paths are spoken as
  file names only.
- D10. Add a task `P5.0` (spike, section A) to PLAN.md in front of P5.1.

## Rules

Inherit rules 1 to 23 (`P3.5.md`, `P3.6.md`, `P4.md`). Plus:

24. Voice is only another way to call `Core.handle` and `client.stop`. No voice module
    reads `ui.token`, imports anything that does, or calls `/approve`, `/deny`, `/undo`,
    `/resume`. A test scans `voice/` for it and a runtime test proves it (section F).
25. The microphone is open only in `listening` (and, with the wake word on, in `idle`).
    `on_state` fires before the stream opens and after it closes.
26. No audio is written to disk and no transcript is stored, except by an explicit debug
    flag that prints where it wrote.
27. A transcript is a request, never a confirmation: while an action waits for approval,
    new speech is not sent to the bridge at all. The only thing a key press does then is
    Stop.
28. No keyboard hook. Global keys go through `RegisterHotKey` only.

## Section B — P5.1 push-to-talk pipeline

Loop with fakes first, then the three real parts, one commit each.

Tests `tests/test_voice_loop.py` (all fakes):
1. Key -> listen -> transcribe -> handle -> speak, in that order, states reported in order.
2. Empty or whitespace transcript: `handle` is not called, state returns to idle.
3. A transcript shorter than 2 words or made only of a known Whisper filler
   ("thank you", "you", "bye"): not sent (list in `config/voice.toml`).
4. `handle` raises `URLError` (bridge down): "The bridge is not running" is spoken, the
   loop survives. `GuardError`: spoken refusal, loop survives.
5. `fresh` per D7 with a fake clock: 30 s later False, 91 s later True.
6. A second key press during `thinking` calls `stop` once and does not start a second
   `handle` (rule 27 groundwork).
7. Answer above 400 characters is cut at a sentence end and the suffix is spoken (D9).
8. `tests/test_core.py`, real `Core` (deferred from the P3.7 G review, Karthik 2026-11-20):
   one `Core` kept alive, a tool request, then the spoken `stop` -> `core.results == []`.
   This pins the reset after `_guard()`; without it "Stopped." carries the last request's
   status lines. Deleting the reset line passes every P3.7 test.
9. Carried from the P4 phase gate (2026-11-25): after `remember_fact` the model replied
   "I've saved that" while the fact was only queued (result `{"queued": True}`; prompt
   rule 8 already says it is saved only after approval). Voice would say this aloud. The
   step-level plan picks the fix (a result that says plainly it is not saved yet, or a
   fixed reply by code as with sources in P4.7) and a test that the reply never claims
   it was saved.

Tests for real parts are thin: `stt` refuses to download (points at a missing local folder
-> clear error, no network attempt; no socket guard exists yet, so the test patches
`socket.socket.connect` to raise);
`tts` returns samples at the voice's sample rate; `audio` is covered by the manual check.

## Section C — P5.2 sentence streaming

`speak(answer)`: split into sentences, synthesise sentence n+1 while n plays (one worker
thread, a queue of at most 2). Tests: order kept; playback of sentence 1 starts before
sentence 2 is synthesised (fake clock and fake synth); an empty sentence is skipped; a
synth error on sentence 2 stops cleanly after sentence 1.

## Section D — P5.3 barge-in

Key during `speaking`: playback stops within 200 ms, the queue is emptied, the state
becomes `listening`. Key during `thinking`: `client.stop()` (core role: no latch), then
listening. Tests: both, plus "the stopped request's answer is never spoken when it arrives
late" (the refused case).

## Section E — P5.4 wake word (off by default)

`config/voice.toml` `wake_word = false`. When true: a small always-on detector on the
microphone stream (16 kHz int16, 80 ms frames); on a hit, same path as a key press but the
task is opened with `untrusted: true` (D3). The detector is built with
`inference_framework="onnx"` (the default, tflite, is not installed on Windows) and model
file paths from the local models folder; `download_models()` is never called at runtime.
The step-level plan first finds where the melspectrogram and embedding models load from. Ignored while speaking (D4). The bridge change for D3 is its own
commit with its own tests in `tests/test_bridge.py` (untrusted task: `create_folder` ->
202; `fresh_context` together with `untrusted` still gives a tainted task; a non-boolean
value is refused), planned and approved separately because it touches `bridge/`.
Tests in the loop: default config never opens the microphone in `idle`; with the wake
word on, state reports `idle (listening for wake word)` so the indicator can show it.

Mic indicator: Windows shows its own icon while any stream is open. Our own indicator is
the `on_state` output: console in P5, tray and panel in P6.2.

## Section F — P5.5 voice cannot approve

1. Static: no file under `voice/` contains `ui.token`, `/approve`, `/deny`, `/undo` or
   `/resume`; `voice` imports nothing from a module that does.
2. Runtime, real bridge on a loopback port: queue a delete through the loop; while it
   waits, feed the transcripts "yes", "approve", "confirm it", "go ahead". Expect: no
   `approve` audit line, `/pending` still lists it, the file exists, and after 120 s the
   outcome is `expired`.
3. The core token on `/approve` -> 403 (exists since P2.2; assert it again here by name).

## Risks

- Latency budget is tight: about 0.6 s silence wait + STT + 1.6 to 2.9 s LLM (P1 numbers)
  + TTS start. Questions about documents now take a median 3.1 s on their own (recall plus
  a second model turn, P4.7 I2 review). Section A decides whether the plan stands.
- Whisper mis-hears paths and names ("Jarvis sandbox" vs `C:\JarvisSandbox`). The prompt
  already maps "my sandbox" to the root; a spoken eval set (20 recorded commands, kept
  local, gitignored) may be needed before the gate.
- Native wheels and Smart App Control.
- Two always-loaded models on the CPU (STT, TTS), three more with the wake word on, while
  Ollama serves the chat and embedding models.
- Upstream pace: no openWakeWord release since 2024-02; faster-whisper's last release is
  2025-10; Piper changed repository and licence in 2025. Exact versions stay pinned in
  `uv.lock`.

## Not in P5

- No voice approval of anything, ever. No voice undo.
- No token streaming from the model (D5), no echo cancellation (D4), no speaker
  verification, no languages other than English.
- No tray icon or animation (P6.2). No start at logon (P8.1).
- No recordings kept.
