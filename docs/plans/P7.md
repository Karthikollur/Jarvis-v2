## Context

PLAN.md P7: a plan -> execute -> verify loop inside budgets; named recipes ("start dev
session": open VS Code on project X, run its dev script, open localhost in the browser);
a browser through Playwright, read-only first, clicks T2, page text tainted. Done when:
3 recipes pass 10/10 runs each.

PLAN.md section 1 already limits this: a 4B model cannot do long-horizon autonomy; v1 is
short supervised workflows of at most 8 tool calls.

## The three problems

1. **Who plans.** 10/10 is a reliability bar a 4b model does not meet by free planning
   (P3.5b needed a quoted example in the prompt to chain three calls). A recipe is
   reliable when its steps are fixed in a file and code walks them.
2. **Verification taints.** The useful checks (`list_windows` shows VS Code, `list_dir`
   shows the file) are tainting tools. Verify after step 1 and every later T1 step needs a
   click. The bridge is right to do this: it cannot know the check's output never reached
   the model.
3. **The browser and the offline rule.** A browser that opens web pages is an outbound
   call. PLAN.md P7.3 and the hard rule in AGENTS.md disagree unless the browser is kept
   to localhost.

## Decisions for Karthik

- D1. Recipes are data, executed by core code, not planned by the model. New
  `config/recipes.toml` (only you edit it): a name, spoken triggers, an ordered list of
  `{tool, args}` steps, and a list of `{tool, args, expect}` checks. The router matches a
  trigger; the core sends each step to the bridge as an ordinary tool request. The policy
  still decides every step; a recipe grants nothing. The model's part: none in v1 (D2).
  Recommended. Alternative: the model picks the recipe and fills parameters.
- D2. Recipes take no parameters in v1 ("start dev session" names one project in the
  file). Parameters arrive with their own plan and their own validation.
- D3. Order inside a recipe: all acting steps first, all checks last. Then taint from the
  checks cannot turn a later step into a click. Cost: a failed step 1 is noticed only at
  the end (each step's own result is still checked as it returns). Recommended.
  Alternative: a bridge notion of "check calls that do not taint", which weakens a
  fail-closed rule and is not recommended.
- D4. Budget: steps + checks <= 8 per recipe, enforced when the file is loaded (a longer
  recipe stops the start, like a bad `apps.toml`). No change to `MAX_CALLS`.
- D5. A failed step stops the recipe. Nothing is rolled back automatically; the report
  names the undo records made so far. Recommended (same rule as `move_files`).
- D6. The dev server. `run_named_script` waits up to 60 s, and a dev server never exits.
  "Start dev session" needs a second kind of script entry in `config/scripts.toml`:
  `detached = true` (started, not waited for, output not returned, so no taint from it),
  still T2, still a fixed argv. That is a `bridge/` and `safety/` change with its own plan
  and refusal tests. Without it recipe 2 cannot pass.
- D7. Browser scope: localhost only in v1. New `config/sites.toml` allowlist of origins,
  shipped with `http://127.0.0.1:*` and `http://localhost:*` only. Every other request,
  including sub-resources a local page asks for, is aborted by request interception.
  Opening the real web is a later decision of the same weight as "optional cloud
  fallback" in PLAN.md section 6. Recommended.
- D8. Browser engine: Playwright driving the installed Edge (`channel="msedge"`), so no
  browser binary is downloaded and Smart App Control sees a signed program. `playwright`
  itself is a dependency for your approval. Check at execution time that Playwright's own
  driver executable starts under Smart App Control.
- D9. Browser tools and tiers: `browser_open(url)` T1 (allowlisted origin only);
  `browser_read()` T0, taints, text only, size cap as `read_text_file`;
  `browser_click(text)` T2. No typing, no form fill, no file upload, no downloads, no
  JavaScript evaluation tool in v1. A fresh profile per bridge start: no saved logins.
- D10. The 10/10 gate and approvals. Three recipes x ten runs with T2 steps is many
  clicks. Options: you click them all; or a gate-only helper you start by hand that
  approves only actions whose tool and arguments equal a step of the recipe under test.
  Not recommended to automate without that exact-match rule; your call.
- D11. PLAN.md P7.1 "plan -> execute -> verify loop": read as the recipe runner (D1, D3).
  Free-form multi-step requests stay what P3.5b made them.

## Shape of the work (order, not steps)

1. `config/recipes.toml` loader and validator; router matches triggers; `Core.handle`
   runs a recipe through `BridgeTool.call`, one task per recipe (rule 15), stops on the
   first failure, returns a spoken summary. Tests with a fake client: order, stop on
   failure, budget refused at load, a step the policy denies ends the recipe and is
   reported (the refused case), checks last, `expect` mismatch reported.
2. `detached` scripts (D6): own plan.
3. Browser tools (D7 to D9): own plan; a dedicated browser thread inside the bridge
   (Playwright's sync objects belong to one thread; routes run in a pool); policy entries
   with tests for a non-allowlisted origin, a redirect to one, a `file:` URL, a
   `javascript:` URL, an origin given with credentials or an odd port form.
4. Three recipes written with Karthik, then `evals/run_recipes.py`: ten runs each, a
   reset of the sandbox between runs, a table of pass / fail per run with the failing step.

## Risks

- The offline rule (problem 3) is a rule conflict in the plan, not a detail: settle D7
  before any browser code.
- A page on localhost is still untrusted text (your own dev server can render data from
  anywhere). Taint applies; the red-team set in P8.4 should include a local page.
- 120 s including approval waits: a recipe with two T2 steps leaves little time for slow
  clicks.
- Recipes are a second route to tools besides the model and the fast path. The runtime
  guard (rule 14) and "every call goes to the bridge" (rule 13) must cover it by test.

## Not in P7

- No model-written plans, no recipe parameters, no loops or conditions in recipes.
- No web browsing beyond the allowlist, no logins, no downloads.
- No scheduling ("every morning"): nothing runs without a request.
