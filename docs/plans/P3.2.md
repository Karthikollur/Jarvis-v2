## Rules for every handler (as P3.1, plus)

1. Paths only from the policy: `args["path"]`, `args["source"]`, `args["target"]` are the
   resolved `Decision.paths`. A handler never builds, joins or re-resolves a path.
   `rename_file` and `move_file` move to `target` and ignore `new_name` / `destination`.
2. Never delete, never overwrite. Every move is `os.rename`, which on Windows refuses an
   existing target and a cross-drive move. A refusal means nothing moved.
3. Files only in v1: `rename_file` / `move_file` refuse a folder and a link
   (`os.lstat`, no follow). Smaller blast radius; the stubs say "file".
4. Act, then record. If the undo record cannot be written, a move is renamed back and the
   call fails. A folder that was created but could not be recorded is left (never deleted)
   and the call fails; the audit line says failed.
5. Results are plain data (`assert_plain`) and carry no untrusted text: `focus_window`
   does NOT return the window title (the tool does not taint, so it must not leak one).
6. No dependency: stdlib + ctypes. No pywinauto in P3.2.
7. A handler that opens a file's content calls `_single_name` on the open handle (refuses
   a hard link; P3.1b G2). None of A to F opens content; a future one brings its own
   hard-link test.

### Design

**Policy (`safety/policy.py`)**
- `MAX_BATCH = 20`.
- `Rule` gains `list_params: tuple[str, ...] = ()` (arguments that are a LIST of paths);
  `Rule.params` includes them, so "all required, nothing undeclared" still holds.
- New entry, strictest tier that works (same as `move_file`):
  `"move_files": Rule(Tier.T1, ("destination",), into=("destination",), list_params=("sources",))`.
- `_resolve` gets one new branch; everything else is untouched:
  - `sources` must be a list of 1..`MAX_BATCH` items; each goes through the existing
    `resolve_inside(..., mutating=True)`. Any refusal refuses the whole batch
    (`sources: <reason>`). The same file twice (normcased) is refused.
  - `destination` is resolved as today (not mutating; may be the root).
  - `paths["sources"]` = tuple of resolved sources; `paths["target"]` = tuple of
    landings `destination / source.name`, each through `resolve_inside(..., True)`
    (refusal labelled `destination: ...`). Two sources landing on the same name
    (normcased) are refused.
  - Added on approval: a source that is already directly inside the destination
    (its landing equals itself, normcased) refuses the batch with
    `sources: already in the destination folder`.
- `Decision.paths` values become `Path | tuple[Path, ...]` (type hint only).
- `_check` / `_recheck` logic unchanged: `recheck` already compares each resolved value
  with the stored one, and tuple equality covers every source and every landing, so a
  junction swapped in while the batch waits is refused. One batch = one budget call.
- `safety/confirm.py`: no change (tuples are immutable; `dict(paths)` is enough).

**Bridge (`bridge/app.py`)**
- `GET /pending`: `"paths"` renders a tuple as a list of strings (today `str(path)`),
  so the UI can list every source and landing. Nothing else: `execute` already merges
  resolved paths over raw args (`{**args, **paths}`), so the handler receives the
  resolved `sources`, `target` and `destination`, never the model's strings.

**Handler (`bridge/tools.py`, inside `mutating`)**
- `move_files(args)`: pairs = `zip(args["sources"], args["target"], strict=True)`.
  1. Preflight, before anything moves:
     - added on approval: `args["destination"]` exists and is a real folder
       (`os.lstat` says directory, and it is not a junction or symlink);
     - every source is a plain file (`os.lstat`, as `_move`);
     - every landing name is free (`os.path.lexists`).
     Any failure raises; nothing has moved.
  2. Move each pair with the existing `_move(source, target, "move_files")`
     (never overwrites; one undo `moved` record per file; an unrecorded move is put back).
  3. A failure on the first file raises (nothing moved). A later failure stops:
     result `{"moved": k, "requested": n, "complete": False, "undo_ids": [...],
     "failed": "<exception class name>"}`. Full success: same shape, `complete: True`,
     no `failed`. No file names or paths in the result (rule 5).
- Reuses `_move` (bridge/tools.py), `UndoLog.moved` (safety/undo.py), `resolve_inside`
  (safety/policy.py). `POST /undo` works per record, unchanged.

**Stub (`evals/stub_tools.py`)**: `tests/test_policy.py` requires `set(TOOLS) ==
set(SPECS)` with matching parameter names, so `SPECS` gains `move_files` (`sources`:
array of paths, `maxItems` 20; `destination`: folder). Consequence: the model sees a
14th tool in the evals, so the evals are re-run in F1 (needs Ollama). If tool selection
falls below the P1 gate (90%), stop and log it under Open questions; no prompt tuning
is improvised.
