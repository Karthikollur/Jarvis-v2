## Context

PLAN.md P6: Tauri 2 + React shell with a floating panel and tray icon; voice state
animation and live task steps; T2 confirmation dialogs as the only approval path; audit log
view, memory manager, hardware monitor; a big Stop button. Done when: every T2 action can
only be approved through the UI; Stop cancels a running task within 1 s.

The UI is the one place a human decision enters the system. Its job in the security model
is narrow: show exactly what the bridge will do, and send approve, deny, stop, resume and
undo with the ui token. Everything it displays came from the model, a file name, a window
title or a document, so everything it displays is untrusted text.

## Design in one page

```
 React (webview)  --invoke-->  Rust (Tauri core)  --HTTP + ui.token-->  bridge 127.0.0.1:8765
        ^                              |
        |  state events                +-- child process: python -m voice  (JSON lines on stdout,
        +------------------------------+                    typed requests on stdin)
```

- The token never enters the webview. Rust reads `ui.token` and exposes a fixed set of
  commands: `pending`, `approve(id)`, `deny(id)`, `stop`, `resume`, `undo_list`,
  `undo(id)`, `health`, plus the P6.4 reads. No generic "call the bridge" command.
- The webview loads only bundled files. Strict CSP (`default-src 'self'`), no remote
  fonts, scripts or images, no Tauri shell, fs, http or dialog plugins for JS.
- The UI polls `/pending` and the events route every 500 ms. No WebSocket in v1.
  `# ponytail: polling; push only if 500 ms is ever felt.`
- Voice and core run as the UI's child process (D2). Its stdout lines are the voice state
  and the request / answer text; the text box in the panel writes requests to its stdin.
- Text from the bridge is rendered as text. No `dangerouslySetInnerHTML`, no Markdown
  rendering of model output, no links made clickable.

## Decisions for Karthik

- D1. What to do if Smart App Control blocks the Tauri binary (section A). Options, yours
  to choose, none decided here: (a) a proper code-signing certificate; (b) keep React,
  drop the Tauri shell, show it in an Edge app window (`msedge.exe --app=http://127.0.0.1:...`,

  panel; (c) a Python-hosted window. AGENTS.md: the stack is not changed without you.
- D2. Process layout: the UI starts and owns the `voice` (core) process; the bridge stays
  independent (P8.1 starts it at logon). Recommended. Alternative: voice posts its state
  to a new bridge route and stays independent of the UI.
- D3. Live steps come from a new ui-role bridge route `GET /events?after=<n>`: an
  in-memory ring of the last 200 audit events (same fields as the audit lines, results
  already cut at 2000 characters). Recommended over the UI reading `audit.jsonl` itself
  for live steps. The audit log view (P6.4) reads the file through Rust, read-only.
- D4. Approval ergonomics, each a guard against an accidental or tricked click:
  the panel never takes keyboard focus when an action arrives; the Approve button is
  disabled for the first 700 ms after its dialog is drawn; keyboard approval is a chord
  (for example `Ctrl+Enter`) that works only while the panel has focus; `Enter` and
  `Space` alone never approve; Deny is the focused default. One dialog per action, no
  "approve all" except the one batch the bridge itself defines (`move_files`).
- D5. Memory manager needs bridge routes (deferred by P4 D6): ui-role
  `GET /memory/pending`, `GET /memory/facts`, `POST /memory/approve`, `/memory/edit`,
  `/memory/delete`, `/memory/forget`, on a second database connection with role `review`.
  Recommended: add them in P6.4, keep the CLI.
- D6. Hardware monitor: a ui-role `GET /stats` that calls the existing `system_stats`
  handler (the UI cannot use `/tool`, which is core-only). Recommended.
- D7. Frontend dependencies: `react`, `react-dom`, `vite`, `typescript`,
  `@tauri-apps/api`, `@tauri-apps/cli`, `vitest`. No component kit, no state library, no
  CSS framework. Rust crates beyond Tauri: an HTTP client (`ureq` or `reqwest`), `serde`.
  Each is a download for your approval.

## Rules

Inherit rules 1 to 28. Plus:

29. The ui token is read by Rust only, at start, and is never sent to the webview, logged,
    or passed to the child process.
30. A confirmation dialog shows the bridge's data: tool, every resolved path from `paths`,
    the reason (`T2` or `tainted T1`), the age and time left. It never shows the model's
    own description of the action.
31. The UI never approves on its own: no timer, no "remember my choice", no default-yes.
32. Every new bridge route is ui-role only, has an entry in `ROUTE_ROLES`, appears in
    `test_route_table_is_exact`, and has a wrong-role refusal test.
33. The child process is started with a fixed command line from the repo; no part of it
    comes from the webview or from bridge data.

## Manual check (Karthik, phase gate)

1. With the UI closed, ask for a delete from the CLI: it waits, then expires. Nothing
   approved it. With the UI open: the card appears, Approve runs it once.
2. Type in another window while a card appears: no keystroke lands on the card.
3. A file named with 200 characters and odd symbols in the sandbox: the delete card shows
   the whole name.
4. Stop during a model turn: the `stop` audit line is within 1 s of the click. Stop during
   a 30 s `run_named_script`: a running handler is not interrupted, so record what Stop
   did and did not cancel.
5. Kill the UI process while an action waits: it expires; nothing ran.
6. Wi-Fi off: the UI starts and works.

## Risks

- Smart App Control and unsigned binaries (section A). Highest risk in the plan.
- The 1 s Stop target against a running handler (`run_named_script` up to 60 s): today
  Stop prevents everything after it but does not interrupt (Decisions 2026-11-11). Either
  the target is read as "no further action within 1 s", or handlers become killable: its
  own plan in `bridge/`.
- "Only through the UI": any process running as Karthik can read `ui.token` (audit point
  6, accepted). The Done-when is met at the level of roles, not against same-user malware.
- Focus and foreground rules on Windows (see P3.2b to P3.2d) for a panel that must be seen
  but must not steal focus.
