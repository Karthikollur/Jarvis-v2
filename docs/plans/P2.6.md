## Design

### 1. Protected folders (audit point 9) — `safety/policy.py`

- `resolve_inside(raw, roots, protected=())`: after the inside-a-root check, a resolved path
  equal to or inside any protected folder raises `PathRefused("protected folder")`. Same
  `realpath` + `normcase` comparison as roots, so junctions and `..` cannot dodge it.
- `Policy(roots, clock, protected=())` passes it through in `check` and `recheck`.
- `bridge/app.py` `create_app(..., protected=None)`: the storage folder is ALWAYS protected.
  `protected=None` (production) adds the repo root (`CONFIG.parent`). Tests pass
  `protected=[]` for the repo part only, because their sandbox lives in the repo's
  `.test-storage`; they cannot switch off storage protection.
- Test fixtures: the sandbox root moves out of the storage folder (today it is
  `storage / "root"`, which would now be refused). Mechanical change in
  `tests/test_bridge.py` helpers that derive storage from `root.parent`.
- A root that contains a protected folder still works for everything outside that folder. A
  root inside a protected folder allows nothing.

### 2. Quarantine and undo records — `safety/undo.py` (new, stdlib only)

`UndoLog(folder, wall=time.time)`, state on disk only (two objects on one folder agree, like
`AuditLog`). One subfolder per record: `<folder>/<id>/record.json`, plus `<id>/item/<name>`
when something was quarantined.

- `quarantine(path, tool) -> Record` — moves the original file or folder into `item/`
  (`shutil.move`, works across drives), writes the record (kind `quarantined`). For deletes
  and for overwrites (call it before writing the new content).
- `moved(source, destination, tool) -> Record` — records a move or rename already done.
- `created(path, tool) -> Record` — records a folder already created.
- `list() -> list[Record]`, newest first. `get(id)`.
- `undo(id, resolve) -> Record` — `resolve` is the policy's path check; every path is
  re-resolved NOW and must come back unchanged, as in `Policy.recheck`:
  - `quarantined`: move the item back to the original path.
  - `moved`: move `destination` back to `source`.
  - `created`: move the folder into quarantine (it becomes a restorable item).
  Refused (`UndoRefused`, nothing moved): unknown id, already undone, original location
  occupied, the thing to move back is missing, path no longer allowed. On success the
  record gains `undone: <ts>` (record file rewritten via temp file + `os.replace`).
- Record fields: `id`, `ts`, `kind`, `tool`, `path`/`source`/`destination`, `undone`.
  No task id in the record: the handler returns the record id in its result, so the audit
  `result` line links record to task.
- No method deletes anything. `# ponytail:` no purge; Karthik empties quarantine by hand
  until size matters.

### 3. Undo routes — `bridge/app.py`

- `create_app` builds `UndoLog(storage / "quarantine")` (folder created, inherits the
  storage ACL from `protect`).
- `GET /undo` (ui): list records. `POST /undo {record_id}` (ui): undo one.
  `ROUTE_ROLES["/undo"] = {"ui"}`.
- Audit, write-before-run as in P2.4: `undo` line (`record_id`, `kind`, paths) before
  anything moves; a failed write -> 500 `Audit log unavailable`, nothing moves. Then
  `undo_result` (`done`, or `refused` + reason). Refusals answer 409 (404 unknown id).
- P3 handlers will get the `UndoLog` when they are wired; P2.6 tests build fake handlers that
  construct their own `UndoLog` on the same folder.

### Limits, to record in Decisions

- A quarantined item keeps the permissions it had; the quarantine folder itself is user-only.
- Cross-drive quarantine copies then removes the source; slow for big files.
- A link swapped in between the undo check and the move is not covered (same recorded limit
  as tools).
- Quarantine grows until Karthik clears it.
- Any same-user process can edit quarantine and records (audit point 6).
