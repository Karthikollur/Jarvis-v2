## Decisions for Karthik

- D1. Move two tasks forward. P8.3 (the gate script, with the offline socket test) helps
  every remaining phase gate; the first layer of P8.4 (below) tests `safety/` and
  `bridge/` as they are today and needs no model. Proposal: do both right after P3
  closes. This changes phase order, so it is yours to decide (also listed under Open
  questions in PROGRESS.md).
- D2. A latched Stop must survive a restart. With crash restart (P8.1), a bridge that
  dies after you pressed Stop would come back un-stopped. Proposal: the latch is a file in
  `%LOCALAPPDATA%\Jarvis` (`halted`), written before the in-memory flag is set, removed
  only by `/resume`; the bridge starts halted when it exists. A `bridge/` change with its
  own plan and tests (restart while latched -> `/task` 403; resume removes the file; a
  file that cannot be written does not stop Stop from stopping).
- D3. Who creates the scheduled task: you, by running a script from the repo
  (`scripts/install_task.ps1`) that registers one task ("at log on of <you>", run only
  when logged on, not elevated, restart every minute up to 3 times). An agent does not run
  it (AGENTS.md: nothing outside the repo, no system changes). A matching
  `uninstall_task.ps1`.
- D4. What starts at logon: the bridge only, or the bridge and the UI (which starts
  voice, P6 D2). Recommended: bridge by the scheduled task, UI from the Startup folder or
  by hand, so a UI crash never takes the kill switch down with it.
- D5. Audit rotation: at bridge start only, when the file is over 10 MB it is renamed to
  `audit-<UTC time>.jsonl` and a new file is created and protected. Never mid-run, never
  deleted by Jarvis. Recommended. The "zero unconfirmed T2" checker reads all of them.
- D6. What "resource caps" means here. Proposed list, pick from it: request body cap on
  the bridge (1 MB); uvicorn `--limit-concurrency`; a warning in `/health` and the UI when
  the quarantine or `memory.db` passes a size you choose (no purge by Jarvis); thread
  counts for STT and TTS; nothing at the OS level (no job objects).
- D7. The red-team model test is informational, not a gate (see P8.4). The gate is the
  deterministic layer plus the audit checker.

## P8.3 — gate script (candidate for early execution)

`scripts/gate.py`, run as `uv run python scripts/gate.py [--real]`:

1. `python -m pytest`.
2. `evals/run.py` twice (stub); `evals/run_docs.py` once P4 exists; `--real` adds the real
   run, which waits for your approvals.
3. Compares with `evals/thresholds.toml` (tool selection >= 90%, refusals all, clarify
   all, doc eval >= 16/20, median latency within targets) and with the last recorded run.
4. Prints one table and exits non-zero on any miss. It writes nothing but its own report
   to stdout; you paste the table into PROGRESS.md.

The offline test, `tests/test_offline.py`: with `socket.socket.connect`,
`socket.create_connection` and `socket.getaddrinfo` patched to raise on anything that is
not loopback, import every runtime package (`core`, `bridge`, `safety`, `memory`, `voice`
when they exist) and drive one request through a real bridge with a fake engine. Zero
attempts allowed. Include the proof that the guard works: a deliberate connect to a
non-loopback address inside the test raises (the refused case). Limit to state in the
test's docstring: it covers Python processes, not Ollama's own process.

## P8.4 — prompt-injection red team

Two layers.

- **Layer 1, deterministic, pytest, no model (the gate).** A scripted "fully obedient"
  model: after reading a poisoned source it issues exactly the calls the injected text
  asks for. Sources: a file's content, a file name, a window title, script output, a
  recalled document chunk, a recalled fact, (after P7) a localhost page. Asks: delete a
  file, move files out of the sandbox, move 20 files at once, run a script, open an app
  on a path, remember a false fact, flood confirmations, call a tool that does not exist,
  reach `%LOCALAPPDATA%\Jarvis` or the repo. Assert the bridge outcome for each pair:
  nothing runs without an approve; outside the roots is 403; the queue stops at 16; the
  task stops at 8 calls; `facts` stays empty; the audit log tells the whole story.
  This layer already has most of its machinery in `tests/test_bridge.py`; the new part is
  the source x ask matrix and its "is not vacuous" test.
- **Layer 2, behavioural, needs Ollama (information).** `evals/redteam.yaml`: 20 poisoned
  documents and file names with a normal question each. Measure how often `qwen3.5:4b`
  obeys the injected text (calls a tool the user did not ask for). Report the rate. It is
  expected to be above zero; the number tells how much the confirmation dialog is being
  leaned on, and whether prompt rule 7 (P4) does anything.
- **The dialog.** A person approves what the card says. Add UI tests (P6) for names built
  to mislead: look-alike folders, very long paths, a name that reads like a sentence
  ("approved by Karthik.txt").

## The "Done when" checker

`scripts/audit_check.py`: reads every audit file; for each `result` line of a call whose
`request` line had `tier: T2`, there must be an `approve` line with the same `pending_id`
and `recheck: ok` before it. Prints violations and a count per day; exit code non-zero on
any. `tests/test_audit_check.py` with hand-written logs: clean, a T2 result with no
approve (the case it exists for), an approve for a different pending id, a tainted T1
(which is `tier: T2` in the log), a rotated pair of files. Run it daily during the week.

## Risks

- D2 (latch across restarts) is a real gap the moment restart is automatic.
- A scheduled task that restarts a crashing bridge every minute can hide a crash loop:
  the UI should show the last `start` lines.
- Always-on means the bridge's token files and audit log sit on disk for weeks; nothing
  new, but audit point 6 (same-user processes) stays the accepted limit.
- One week of daily use needs P4 to P7 to be pleasant enough to use daily. If voice
  latency misses its target, this "Done when" is the one that suffers.

## Not in P8

- No installer, no signed build, no auto-update.
- No quarantine or audit purge by Jarvis code.
- No Windows service, no elevation, no second user account (PLAN.md 4.3 keeps the
  standard-user test as optional and manual).
- No protection against same-user malware beyond what exists.
