# P3.2c — `focus_window` waits for the activation to land

Planner: Claude Code (Opus 5.5), 2026-11-14. Status: APPROVED by Karthik 2026-11-14.
Not implemented. Implementer: Cursor.

## Context

Karthik's manual check of P3.2b on 2026-11-14 (running bridge, audit log read back):
`focus_window` "notepad" was allowed (T1, untainted), and 22 ms later the handler raised
`OSError: Windows refused to bring the window forward`.

A read-only diagnosis against the same Notepad window showed that Windows did not refuse:

```
SetForegroundWindow -> 1        (accepted)
  0 ms  GetForegroundWindow -> None      (no foreground window during the handoff)
 25 ms  GetForegroundWindow -> Notepad   (and stays Notepad)
```

`_to_front` reads `GetForegroundWindow()` once, right after the call. It gets `None`, takes
`if not front: return False`, and never reaches the attach path. The tool reports a failure
while Notepad comes forward. The fakes could not show this: `FakeUser32` changes
`foreground` synchronously.

Activation crosses processes: `SetForegroundWindow` posts the request and the target
window's own thread completes it when it pumps messages. Any check made in between sees no
foreground window.

Outcome wanted: "focus notepad" through a running bridge answers `focused: True` when
Notepad came forward, and still fails honestly when Windows really refuses.

## Scope

One code commit, `P3.2c: focus_window waits for the activation`. Only `bridge/tools.py` and
`tests/test_tools.py` change in code, plus docs. Nothing in `safety/`, `config/`, routes, or
the policy entry. No new dependency (`time` is already imported in `bridge/tools.py`).

## Design (`bridge/tools.py`)

New helper beside `_to_front`:

```
_settled(hwnd, timeout=0.25, step=0.01) -> bool
    deadline = time.monotonic() + timeout
    while True:
        if _user32.GetForegroundWindow() == hwnd: return True
        if time.monotonic() >= deadline: return False
        time.sleep(step)
```

`_to_front` changes in exactly two places:

- Step 1: `SetForegroundWindow(hwnd)`, then `if _settled(hwnd): return True`.
- Step 5: after the attached call and the `finally` detach: `return _settled(hwnd)`.

Everything else stays as P3.2b: the guards (`not front`, own thread, hung), one attach,
detach in `finally`, the `OSError` text, the `{"focused": True}` result. `front` is read
after `_settled` returned False, so the guards see the real foreground window, not the
transient `None`.

Ceiling comment on `_settled`:
`# ponytail: 250 ms cap; make it config if a slow app needs more`.

Why this is not the "retries or sleeps" P3.2b excluded: the focus request is still issued
at most twice (plain, then attached), exactly as in P3.2b. The wait only polls a read-only
query, to confirm an activation Windows already accepted. Worst-case added latency is
500 ms, and only when the window never comes forward, which ends in an error anyway.

## Tests (`tests/test_tools.py`, tests first, red run shown)

`FakeUser32` learns `settles_after` (default 0 = today's behaviour): when
`SetForegroundWindow` would change `foreground`, the fake instead answers the next
`settles_after` reads of `GetForegroundWindow()` with `None`, then the target.

Fake clock: the `desktop` fixture replaces the **module reference** `tools.time` with a
small fake object (`monotonic()` returns a counter, `sleep(s)` advances it and counts the
call) via `monkeypatch.setattr(tools, "time", fake)`. Do not patch attributes of the real
`time` module (`tools.time.sleep = ...` would change `time.sleep` for pytest itself).

The existing 21 `focus_window` tests keep passing unchanged. New tests:

1. Plain call accepted, foreground settles after 2 reads: `{"focused": True}`, no attach
   in the log. (The bug from the manual check; red against today's code.)
2. Attached call accepted, settles after 2 reads: the full P3.2b call log,
   `{"focused": True}`.
3. Never settles (the foreground stays another window, Windows refuses even attached):
   `OSError`, and the fake clock shows a total wait of at most 2 x 250 ms plus one step.
4. Settles too late (`settles_after` larger than the 250 ms budget allows): `OSError`. The
   cap is real.
5. Transient `None`, then another window that is not the target: the guards run on that
   real window and the attach happens once.

Mutants (in memory, baseline first, table added here when implemented):

| Mutant | Must be killed by |
|---|---|
| no wait at all (today's code) | test 1 |
| no deadline (loops until it sees the target) | test 3 (harness caps sleep calls) |
| deadline but never sleeps (busy spin) | a sleep-count assertion in test 1 or 3 |
| wait only on the plain path | test 2 |
| wait only on the attached path | test 1 |
| `front` read before the wait | test 5 |
