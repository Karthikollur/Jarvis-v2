# P3.2b — `focus_window` gets the foreground (AttachThreadInput)

## Context

Karthik's manual check on 2026-11-13 (running bridge, audit log read back):
`open_app` works, the allowlist refusal works, but `focus_window` fails with
`OSError: Windows refused to bring the window forward`. The window was found and the
policy allowed the call. Windows has a foreground lock: only the process the user is
currently working in may push another window to the front. The bridge is a background
process, so `SetForegroundWindow` is refused. The handler fails honestly, but the tool
does not work in real use. Karthik chose option (a): attach to the foreground thread's
input around the call.

Outcome wanted: "focus notepad" brings Notepad to the front through a running bridge, and
when Windows still refuses, the tool still says so (never a false `focused: True`).

## Scope

One code commit, `P3.2b: focus_window gets the foreground`. Only `bridge/tools.py` and
`tests/test_tools.py` change, plus docs. Nothing in `safety/`, `config/`, routes, or the
policy entry (`focus_window` stays T1, one short printable `title`, confirm when tainted).
No new dependency: ctypes and the standard library only.

## Design (`bridge/tools.py`)

New private helper next to `focus_window`; `focus_window` calls it instead of calling
`SetForegroundWindow` directly. Matching, `_candidates()`, the minimised-window restore
(`IsIconic` -> `ShowWindow(SW_RESTORE)`) and the result `{"focused": True}` are unchanged.

```
_to_front(hwnd) -> bool
  1. SetForegroundWindow(hwnd). If the foreground window is now hwnd: True.
  2. front = GetForegroundWindow(); theirs = GetWindowThreadProcessId(front, None);
     ours = threading.get_native_id().
     No foreground window, or theirs == ours: False.
     IsHungAppWindow(front): False, no attach (added on approval: attaching to a
     thread that does not pump messages can stall the bridge's own input).
  3. AttachThreadInput(ours, theirs, True). Refused: False
     (Windows refuses for an elevated window; the tool then fails honestly).
  4. try: SetForegroundWindow(hwnd)
     finally: AttachThreadInput(ours, theirs, False)   # always detached
  5. Return GetForegroundWindow() == hwnd.
```

- `focus_window`: `if not _to_front(hwnd): raise OSError("Windows refused to bring the
  window forward")` (same text as today, so the audit line stays comparable).
- Success is judged by `GetForegroundWindow() == hwnd`, not by the return value of
  `SetForegroundWindow`: Windows can answer "ok" and only flash the taskbar button. This
  makes the existing success path stricter, on purpose.
- `argtypes` / `restype` declared for the new calls, like the existing block at the top of
  the file (`GetForegroundWindow` -> `HWND`; `AttachThreadInput(DWORD, DWORD, BOOL)`;
  `SetForegroundWindow(HWND)`; `IsHungAppWindow(HWND)`; `GetWindowThreadProcessId`
  already declared).
- `threading.get_native_id()` gives the calling thread's Windows thread id, so
  `_kernel32` needs no new call and the tests need no kernel32 fake.
- The `ponytail:` comment on the old line is replaced by one naming the ceiling: if
  Windows still refuses, the UI (P6, a foreground process) is the place to focus from.

Why this is safe to add: attaching shares keyboard state and focus with the foreground
thread for the length of one call and is always undone in `finally`. It grants no new
right: Windows refuses the attach across privilege levels (an elevated window), and that
refusal is reported as a failure. The policy check, the taint rule and the audit line are
untouched.

## Tests (`tests/test_tools.py`, tests first, red run shown)

`FakeUser32` (existing, fakes only, no real window touched) learns: a `foreground` handle,
`GetForegroundWindow`, `GetWindowThreadProcessId(hwnd, None)` (thread id per handle),
`IsHungAppWindow` (a set of hung handles),
`AttachThreadInput` (records the call; can be set to refuse), and a `SetForegroundWindow`
that changes `foreground` only when allowed: `refuses` (always), `needs_attach` (only
while attached), `lies` (returns True, changes nothing).

Existing five `focus_window` tests keep passing with the richer fake (direct success path:
no attach call is made). New tests:

1. Refused directly, accepted once attached: the full log is the plain foreground
   call, then attach(True), foreground, attach(False), with both thread ids; result
   `{"focused": True}`. (Karthik, 2026-11-14: include the plain call.)
2. Refused even when attached: `OSError("refused")`, and the detach still happened.
3. Attach itself refused (elevated window): `OSError`, no second foreground call, no detach.
4. No foreground window (handle 0): `OSError`, no attach attempted.
5. The foreground thread is the bridge's own thread: `OSError`, no attach attempted.
6. `SetForegroundWindow` says True but the foreground did not change: `OSError`
   (no false `focused: True`).
7. Minimised window with `needs_attach`: restore first, then the attach sequence.
8. Added on approval: the foreground window is hung (`IsHungAppWindow` true): `OSError`,
   no attach attempted, no second foreground call.
9. Test 9, added in implementation, approved by Karthik: `SetForegroundWindow` raises
   while attached. The exception propagates, and the log shows
   `AttachThreadInput(..., False)` still happened.

Mutants, in memory (same harness as F1/F2, baseline run first), reported as a table:
no attach at all (= the pre-fix code, which is the red run); no detach; detach not in
`finally` (skipped when the call raises); attach failure ignored; attaches to its own
thread id; success taken from the return value instead of `GetForegroundWindow`;
attach before trying the plain call (every focus attaches); added on approval: no hung
check.
